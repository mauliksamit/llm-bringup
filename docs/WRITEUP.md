# Write-up — bringing up and optimizing TinyLlama-1.1B on an RTX 5070 Laptop

All numbers come from `results/` (checked by `scripts/claims_audit.py`).
Tables between markers are generated by `scripts/summarize.py`.

## 1. Setup

- Model: `TinyLlama/TinyLlama-1.1B-Chat-v1.0`, revision
  `fe8a4ea1ffedaf415f4da2f062534de366a451e6`, Apache-2.0, 1,100,048,384
  parameters (counted from the safetensors header), file hashes in
  `results/model_files.json`.
- Hardware/software: RTX 5070 Laptop GPU (sm_120, 8 GB, 75 W power cap,
  WDDM), driver 617.14, torch 2.14.1+cu130, transformers 5.19.0 (reference
  only), Windows 11. Every result JSON records its environment and commit.
- Evaluation text: Project Gutenberg #1342 (public domain), first 40,000
  characters after Chapter I (`data/eval_text.meta.json`).

## 2. Bring-up

`llm_bringup/model.py` is a from-scratch Llama forward pass: embedding,
RMSNorm (float32 statistics, cast back), RoPE in rotate-half form with
float32 tables, grouped-query attention (32 query heads, 4 KV heads), SwiGLU
MLP, untied LM head. q/k/v and gate/up weights are concatenated at load time
so each is one GEMM; this holds in every configuration, baseline included.

Validation, in two layers:

1. **Unit level** (`tests/test_model.py`): a tiny random-weight Llama built
   in `transformers` and loaded into our code must give the same logits
   (tolerance 1e-4, justified in the file) for both attention paths;
   incremental decode with both cache types must equal the full forward;
   greedy tokens must equal `hf.generate`. A deliberately broken
   `rotate_half` fails the comparison, so the test is not vacuous.
2. **Real weights** (`scripts/reference.py`, `scripts/numerics.py`): the
   reference is `transformers` in float32 on the CPU. Our FP32 GPU model:
   teacher-forced token match 100.0%, free-running greedy match 100.0% on
   three 32-token continuations, perplexity 6.7475 against the reference's
   6.7475 (`results/numerics/s0_fp32_baseline.json`).

## 3. Measurement protocol

`scripts/bench.py`: greedy generation of 64 new tokens; TTFT = prefill
forward + first argmax; decode = the remaining 63 steps; CUDA events only,
inputs already on the GPU. 10 warmup and 30 timed generations per cell;
median, p95, min and raw values saved; nvidia-smi clock/power samples before
and after each cell. Every step is run twice; `scripts/check_drift.py` flags
any median that moves more than 5%; flagged steps get a third run
(`scripts/adjudicate.py`). Reported value = median of the per-run medians.
Every timed generation in every run produced identical tokens.

### s0 — FP32 baseline
Naive attention (explicit matmul, float32 softmax), KV cache grown with
`torch.cat`, composed RMSNorm. Stable: all 8 medians within 1.34% between
runs. Batch-1 decode at p128 takes 19.034 ms/token.

### s1 — BF16 (hypothesis: prefill is GEMM-bound, decode bandwidth-bound)
Prefill confirmed: TTFT 3.15x faster at b4 p128 (tensor cores; FP32 runs
with TF32 off). Decode refuted: only 1.11x at b1 p128, and decode time is
nearly the same at batch 1 and batch 4. The traces show why (section 5):
GPU busy time halves but the GPU sits idle waiting for launches. Numerics:
max abs logit diff 1.722, perplexity 6.7468 (reference 6.7475), teacher-forced
match 97.6%; free-running greedy match drops to 69.8% because two text
prompts reach a near-tie after 12 tokens and then diverge — reported, not
hidden. Run 1 vs 2 flagged three batch-1 cells; run 3 was adjudicated (the
per-run minimums agree, the medians move with CPU-side noise).

### s2 — scaled_dot_product_attention
Removes the score matrix and ~8 attention kernels per layer; GQA handled
natively. TTFT 2.15x faster at b1 p1024 and 2.10x at b4 p1024; decode 1.44x
at b1 p128; peak memory 2.79 GiB at b4 p1024. Kernels per generated token
fall from 1109.7 to 866.3 (section 5).

### s3 — static KV cache (a regression in eager mode)
First version: slower everywhere. The traces counted 704 extra `arange` and
704 extra compare kernels in 16 decode steps — the decode mask was rebuilt in
every layer — and prefill took a masked path over the whole preallocated
length. After fixing both (mask once per forward; causal prefill over the
prompt), TTFT matches s2 but decode is still slower in eager mode (0.82x at
b1 p128). The step stays because CUDA graphs need fixed shapes and addresses.
See `docs/NEGATIVE_RESULTS.md`.

### s4 — CUDA-graph decode
One decode step (forward, argmax, position and output bookkeeping) captured
once per (batch, prompt) config and replayed per token. Decode 1.88x faster
than s3 at b1 p128 (7.738 ms/token), run-to-run drift of decode medians
0.00–0.40%. TTFT rose 5–13% although prefill code is identical; nvidia-smi
samples put the GPU at its 75 W power cap with lower SM clocks during these
runs, the likely cause (two samples per cell; not proven).

### s5 — fused RMSNorm kernel
`llm_bringup/kernels/rmsnorm.cu`, written from scratch: one block per row,
float32 sum of squares with a warp-shuffle block reduction, 16-byte vector
loads/stores when aligned, and the same rounding sequence as the PyTorch
composition. Correctness gate before speed (section 7). In the model:
decode 1.05x and TTFT 1.22x over s4 at b1 p128, and kernels per token
984.4 → 669.4 (32.0% fewer). Both s4 and s5 ran at the power cap, so this
TTFT comparison is like-for-like. Numerics: perplexity 6.7507; the kernel is
bit-identical to the composition for >99% of bf16 outputs, not all.

**Baseline → final** (b1 p128): TTFT 3.07x, decode 2.58x, peak memory
4.18 → 2.16 GiB; at b4 p1024: TTFT 4.90x, decode 2.81x (`docs/FACTS.md`).

Reading the table (batch 1, prompt 128, 16 new tokens per trace):

- **GEMV/GEMM dominate busy time** in every step (heuristic name
  classification): decode at batch 1 multiplies a vector by each weight
  matrix. Attention is a small share even at its peak.
- **Launch gaps dominate wall time until s4.** BF16 halves busy time
  (232.3 → 117.7 ms) but idle rises from 42.0% to 73.3%. CUDA graphs take
  idle from 65.0% to 12.5%; the fused kernel brings it to 7.2%.
- **Elementwise kernels are many but cheap.** Their share falls when the
  RMSNorm composition (about seven small kernels per call, 45 calls per
  forward) becomes one kernel.

## 6. Counter-level check of the decode GEMVs (Nsight Compute)

`scripts/ncu_decode_step.py` + `scripts/ncu_decode_summary.py`: every cuBLAS
GEMV of one batch-1 decode step (s2 config), ncu 2025.3.1 with clocks
unlocked, metric names confirmed by `ncu --query-metrics`.

- DRAM bytes read / analytical weight bytes: 1.001–1.026 per projection —
  every token streams the 2.07 GB of weights from DRAM.
- `dram__throughput`: 87.0–98.1% of peak sustained (92.8% time-weighted).
- GEMV time for the step: 6446.5 us under the profiler.

So at batch 1 the remaining decode time is the weight read; further kernel
tuning has little room. Analytical estimate (labeled): comparing that GEMV
time with the final graph decode at b1 p128 (7.384 ms/token) suggests most of
the remaining step is weight streaming — the two numbers come from different
conditions (profiler vs timed run), so this is an estimate, not a measurement.

## 7. The custom kernel: correctness, sanitizer, speed

- Correctness (`tests/test_fused_rmsnorm.py`, 69 cases): float32/bf16/fp16,
  hidden sizes 1, 7, 8, 64, 2047, 2048, 5632, rows 1, 3, 1024, large and
  small magnitudes, an unaligned view (scalar path), 3-D input; tolerance
  one output ulp (justified in the file).
- Compute Sanitizer: memcheck, racecheck, synccheck, initcheck all clean
  (`results/sanitizer/`).
- Speed (`scripts/bench_rmsnorm.py`, graph-replayed so CPU launch overhead is
  excluded; 3 runs): see the kernel table above. Eager-mode timings were also
  recorded but drifted 15–37% between runs (launch noise) and are not used.
  Throughput figures are cache-warm effective values, not DRAM bandwidth.

## 8. What transfers, and what does not

Transfers to any accelerator stack: validating a new implementation against
an independent reference before optimizing; reporting precision effects with
teacher-forced and free-running metrics; separating "the device is busy"
from "the device is waiting" with traces before touching kernels; confirming
the bound with counters; and accepting a locally slower step when it enables
a larger structural win (static shapes for graph capture — the same property
ahead-of-time compiled execution relies on).

Does not transfer directly: the specific kernels (cuBLAS GEMV, SDPA backends),
CUDA-graph mechanics, warp-level reduction details, and every absolute
number — they are specific to this GPU, driver, and laptop power envelope.
