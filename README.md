# llm-bringup — bring up and optimize a 1.1B Llama on one consumer GPU

TinyLlama-1.1B (Llama architecture: RMSNorm, RoPE, grouped-query attention,
SwiGLU) implemented **from scratch in PyTorch** (no `transformers` in the
model code), validated against an independent reference, then optimized one
measured step at a time on an RTX 5070 Laptop GPU — ending with a
from-scratch fused RMSNorm CUDA kernel. Every number below is generated from
`results/` by a script; `python scripts/claims_audit.py` fails on any
number in this README or `docs/` that cannot be traced to a stored result.

## What was done

1. **Bring-up.** `llm_bringup/model.py` loads the safetensors checkpoint
   (TinyLlama-1.1B-Chat-v1.0 at revision `fe8a4ea1`, Apache-2.0) into a
   hand-written decoder. Correctness: unit tests against a random-weight
   `transformers` Llama, then the real weights against `transformers` in
   float32 on the CPU (logits, greedy tokens, perplexity on a public-domain
   text).
2. **Measurement.** TTFT, decode tokens/s and peak memory for batch {1, 4} x
   prompt {128, 1024}, CUDA events, 10 warmup + 30 timed generations, every
   step run twice with a scripted 5% drift check (third run when flagged).
3. **Optimization ladder** (one change per commit, each with numerics and a
   profiler trace): FP32 → BF16 → `scaled_dot_product_attention` → static KV
   cache → CUDA-graph decode → fused RMSNorm kernel.
4. **Analysis.** Where GPU time goes per step, from the traces, using
   [perflens](https://github.com/mauliksamit/perflens); Nsight Compute counters
   on the decode GEMVs; a kernel-level benchmark and Compute Sanitizer for the
   custom kernel. Full write-up: [`docs/WRITEUP.md`](docs/WRITEUP.md).

## Key findings

- **Bring-up is exact enough to trust.** The from-scratch FP32 model matches
  `transformers` FP32 on the CPU with 100.0% teacher-forced and 100.0%
  free-running greedy token agreement on all reference sequences.
- **Decode was launch-bound, not bandwidth-bound, until CUDA graphs.** BF16
  halved GPU busy time (232.3 → 117.7 ms in the traced generation) but GPU
  idle time rose from 42.0% to 73.3%: the GPU waited on the CPU. CUDA graphs
  cut idle from 65.0% to 12.5%.
- **Then the weights are the floor.** Nsight Compute on the decode GEMVs:
  DRAM bytes read equal the weight bytes (1.001–1.026x) and DRAM throughput
  is 87.0–98.1% of peak, so at batch 1 each token streams all 2.07 GB of
  weights.
- **A step can be a regression and still be necessary.** The static KV cache
  made eager decode slower (documented in `docs/NEGATIVE_RESULTS.md`) but is
  what makes CUDA graphs possible.
- **The custom kernel is correct before it is fast**: 69 correctness cases,
  Compute Sanitizer memcheck/racecheck/synccheck/initcheck clean, then
  5.10–18.04x faster than the composed PyTorch RMSNorm in GPU time, and
  32.0% fewer kernels per generated token in the model.

## Reproduce

```bash
python -m venv .venv && .venv/Scripts/python -m pip install -r requirements.txt   # (bin/ on Linux)
python scripts/download_model.py          # pinned revision, no login
python scripts/fetch_eval_text.py         # public-domain eval text (already committed)
python -m pytest -q                       # GPU tests skip without CUDA
python scripts/reference.py               # transformers FP32 CPU reference (~4-6 min)
bash scripts/run_step.sh s0_fp32_baseline .venv/Scripts/python.exe   # numerics, bench x2, drift, trace
# ... s1_bf16, s2_sdpa, s3_static_kv, s4_cuda_graph, s5_fused_rmsnorm
python scripts/trace_breakdown.py ../perflens   # needs a perflens checkout
python scripts/summarize.py && python scripts/facts.py && python scripts/claims_audit.py
```

The fused kernel (`s5`) JIT-builds with `torch.utils.cpp_extension`; on
Windows run inside a Visual Studio developer prompt with `CUDA_HOME` set.
Hardware and software of every run are recorded in each result JSON.

## Scope and limitations

One GPU (RTX 5070 Laptop, 8 GB, 75 W power cap, Windows/WDDM), one model, a
4-cell batch/prompt grid. `torch.compile` is NOT RUN here (no Triton on
native Windows). This is a CUDA project: it makes no claims about other
accelerators. See [`docs/LIMITATIONS.md`](docs/LIMITATIONS.md) and
[`docs/NEGATIVE_RESULTS.md`](docs/NEGATIVE_RESULTS.md).
